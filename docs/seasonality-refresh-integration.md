## Repeat-build defect and narrowly scoped fix

The real archive run generated **133 public/calendar entries** from **30,288 eligible archive records**, with 30 arrivals and 30 departures. Validation then rejected **60 no-op timing change rows**. A separate disposable reproduction using the already validated public CSV confirmed the same failure, so it is not caused by the SQL path redirection or regenerated public layer.

Root cause in the existing generator: previous CSV months are strings, while newly calculated months are numbers. The change-report comparison uses strict equality before serialization (`'4' !== 4`), then writes identical old/new CSV values (`4 -> 4`). The validator correctly rejects those no-op records and the build writes FAILED metadata. This is a repeat-build change-accounting defect, not evidence of changed migration timing.

Logs (private local evidence):

- `/private/tmp/hf-refresh-real-run.log`
- `/private/tmp/hf-refresh-change-report-diagnostic.log`
- `/private/tmp/hf-refresh-change-report-diagnostic-20261023/` (explicit disposable FAILED fixture)

The fix converts both old and new change-report values to strings before comparison. This changes only change-accounting representation: month calculations, classification, confidence, validation rules, metadata generation and schemas remain unchanged. No history is cleared. Five new regression tests exercise identical-input replay, unchanged numeric months, a genuine month change, unchanged confidence and unchanged movement type. A genuine `4 -> 5` change survives a further replay without additional rows.
